# SENTINEL 项目讲解（中文）

这份文档讲清楚三件事：**这个 demo 在做什么、每一步背后的原理、上台时可能被问到什么**。代码细节以 `backend/` 和 `frontend/src/` 为准。

---

## 一、一句话概括

一个**安全分析师助手（SOC Copilot）**：收到一条可疑告警后，它会
1. 解码被混淆的命令；
2. 用 **Qdrant** 在 ATT&CK 和 Sigma 规则库里判断“这是什么攻击”；
3. 用 **Qdrant** 在全公司日志里找出“行为相同但没有报警”的其他主机；
4. 用 **Cognee** 知识图谱推断“可能是哪个黑客组织、下一步会做什么、该怎么防”；
5. 生成事件报告和一条新的检测规则。

全部在本机运行：不需要 API Key、不需要 Docker、不需要联网。

## 二、整体架构

```
                    ┌──────────────── 一次性导入（backend/build.py）────────────────┐
MITRE ATT&CK 数据 ──┤→ Qdrant 集合 threat_kb   ：697 个攻击技术 + 2,410 条 Windows Sigma 规则
SigmaHQ 规则库   ──┘                              每条同时存 dense 向量 + sparse(BM25) 向量
合成日志(scenario) ─→ Qdrant 集合 endpoint_logs ：1,282 条进程事件，27 台主机，藏着 1 次入侵
ATT&CK 关系数据  ──→ Cognee 知识图谱            ：1,785 个节点 / 约 19,000 条边
                                                  （图存在 Ladybug，节点向量也存进 Qdrant）

浏览器（three.js 3D 界面） ⇄ FastAPI 后端（backend/app.py） ⇄ Qdrant / Cognee
```

| 组件 | 作用 | 说明 |
|---|---|---|
| Qdrant 1.19（macOS 原生二进制） | 向量数据库 | `bin/qdrant`，数据在 `storage/` |
| FastEmbed `bge-small-en-v1.5` | 本地文本向量模型（384 维） | CPU 即可，无需 Key |
| FastEmbed `Qdrant/bm25` | 稀疏向量（关键词） | 配合 Qdrant 的 IDF 修正 |
| Cognee 1.4.2 + Qdrant 社区适配器 | 知识图谱 + 记忆 | 图结构在 Ladybug，向量索引在 Qdrant |
| FastAPI | 后端 API | 端口 8916 |
| three.js + 3d-force-graph | 3D 拓扑与知识图谱 | esbuild 打包，离线可用 |

## 三、演示用的“故事”（backend/scenario.py）

一家虚构公司，27 台主机，分 5 个网段（DMZ、服务器、财务、HR、研发）。

**攻击链：**
1. 09:12 财务员工 `j.meyer` 在 **WS-FIN-07** 打开带宏的 `Invoice_Q3_2026.docm`
2. Word 启动了**编码过的 PowerShell**，下载并执行 `http://cdn-update.cloud/a.ps1` → 🔴 触发严重告警
3. 用 `rundll32 comsvcs.dll MiniDump` **转储 LSASS 内存**（偷密码）→ 触发高危告警
4. 用 `wmic /node:` 通过 **WMI 横向移动**到 3 台机器：**WS-FIN-03、FS-01、WS-HR-02**
5. 这 3 台机器上跑的 PowerShell **载荷各不相同**（写法、参数、C2 地址都变了），所以**签名规则一个都没报**

**故意埋的“干扰项”：**
- 公司的 Intune 管理脚本同样是 `-WindowStyle Hidden -EncodedCommand`，看起来和恶意命令很像，其实是正常的——这是 SOC 里最典型的误报来源。
- 另有 5 条日常低危告警（VPN 登录失败、扫描器 UA 等），让告警队列看起来像真实环境。

> 所有日志都是用固定随机种子生成的，每次结果一致，演示可重复。

## 四、每一步的原理

### ① 解码与富化（本地，不涉及数据库）
- 用正则找出 `-enc / -e / -EncodedCommand` 后面的 base64，按 **UTF-16LE** 解码（PowerShell 的编码规则）。
- 提取 IOC（URL、IP）和可疑特征（`IEX`、`DownloadString`、`-w hidden` 等）。
- **关键设计：向量化的是“解码后的行为”，而不是乱码。** 嵌入文本的格式是
  `父进程 spawned 子进程 [encoded command]: 解码后的命令`。
- 另一个细节：**嵌入文本里去掉了主机名和用户名**。早期测试发现，带上 `j.meyer` 会让模型靠用户名“作弊”找到受害机，这不真实。

### ② 映射到 ATT&CK + Sigma（Qdrant 混合检索）
对每条告警同时发三种查询到 `threat_kb`：

| 方式 | 原理 | 擅长 | 弱点 |
|---|---|---|---|
| **Dense（稠密向量）** | 语义相似度 | 理解“意思”，同义表达 | 对精确词（DLL 名、函数名）不敏感 |
| **Sparse（BM25）** | 关键词匹配 + IDF 权重 | 精确 token，如 `comsvcs`、`MiniDump` | 不懂语义 |
| **Hybrid（RRF 融合）** | 两路各取前 40，按排名倒数融合 | 两者兼得 | — |

Qdrant 的写法是 `query_points(prefetch=[dense, bm25], query=FusionQuery(RRF))`，一次请求完成。

**真实跑出来的结果（不是摆拍）：**
- 第一条（PowerShell 下载）：三种方式都能找到 `T1059.001 PowerShell` 相关规则。
- 第二条（`comsvcs.dll MiniDump`）：**Dense 完全找偏**（返回一堆无关的 rundll32 规则），**BM25 精准命中** `T1003.001 LSASS Memory` 和 “Process Memory Dump Via Comsvcs.DLL” 规则，**Hybrid 两边的好结果都保留了**。这是讲混合检索价值的最佳例子。

**技术识别：** 对 Hybrid 前 5 条结果里的 ATT&CK 编号按排名加权投票（第 1 名 1 分，第 2 名 0.5 分……），权重 ≥ 0.4 才保留，得到 `T1059.001`、`T1003.001`。

### ③ 狩猎相似行为（Qdrant 分组检索 + Recommend API）
问题：**“只有 WS-FIN-07 中招了吗？”**

**阶段一：相似度检索**
- 以告警事件本身（点 ID）为查询，在 `endpoint_logs` 里找最相似的事件；
- 过滤：只看进程创建事件，排除 WS-FIN-07 本身；
- `group_by=host`：**每台主机只返回最像的一条**，结果直接是“主机排行榜”。
- 结果：前 3 名是 3 台真实受害机，但**第 4～8 名全是 Intune 正常脚本**，而且分数差距很小（约 0.86 vs 0.84）。

**阶段二：Recommend API（加入反例）**
- 正例：这条告警；反例：7 种“已知良性（allowlist）”行为；
- 策略 `average_vector`：查询向量 ≈ 正例 − 反例，把“像 Intune 脚本”的方向推开；
- 结果：Intune 类伪装者从榜单消失，第 4 名以后变成完全无关的 Word 打开事件。

**怎么判定“被入侵”：** 对 40 台主机的得分算 **z-score**（与平均值相差几个标准差），**z ≥ 1.0 且不在白名单**的判为失陷。结果恰好是 WS-FIN-03（z≈3.3）、FS-01（z≈1.9）、WS-HR-02（z≈1.1）。

**横向移动路径：** 不是写死的——从 WS-FIN-07 自己的日志里解析 `wmic /node:XXX` 得到“谁连了谁、几点”，3D 界面上的红色弧线就是它。

> ⚠️ **诚实说明**：阶段一其实已经把 3 台受害机排在最前面了。Recommend 的真实作用是**清除长得像的误报**，而不是“凭空找出受害机”。上台时请这样表述，懂行的人会认可。

### ④ 知识图谱推理（Cognee）
**图是怎么建的：** 直接用 ATT&CK 官方的关系数据，通过 Cognee 的 `add_data_points` 写入（**没有让 LLM 抽取**，所以每条边都可追溯到 MITRE）。节点类型：

```
ThreatGroup(黑客组织) ─uses→ Technique(技术) ─in_tactic→ Tactic(战术阶段)
ThreatGroup ─uses_software→ Software(工具/恶意软件) ─uses→ Technique
Mitigation(缓解措施) ─mitigates→ Technique
Asset(公司主机)、Incident(事件，演示时动态写入)
```

**推理过程（`backend/copilot.py` 的 `reason`）：**
1. **补全观察到的技术**：把狩猎中发现的证据（3 条 wmic 横向命令 + 3 台受害机上的命令）再送回 Qdrant 检索，一个技术**至少被 3 条证据命中**才采纳 → 新增 `T1047 WMI`。最终观察到：`T1059.001`、`T1003.001`、`T1047`。
2. **归因**：遍历所有 176 个组织，按“与观察到的技术重合个数”排序；重合数相同时，偏向**技能库更小（更有特征）**的组织。当前前三：Blue Mockingbird、GALLIUM、Indrik Spider（阈值一改，名单可能变化，排练以最终版为准）。
3. **预测下一步**：取前三组织会用、但还没观察到的技术，只看后续阶段（凭证获取、发现、横向移动、收集、C2、外传、影响、提权），**至少 2 个组织都会用**的才算，取前 5。当前结果如计划任务、RDP、远程系统发现、工具下载、本地数据暂存。
4. **缓解措施**：找覆盖“观察到 + 预测到”技术最多的 4 条 Mitigation。
5. **写回记忆**：把这次事件作为 `Incident` 节点（关联技术、受害主机、疑似组织）用 `add_data_points` 写回 Cognee，耗时约 1 秒。下次调查可以从这段记忆出发。

> 说明：DC-01/DC-02 显示为黄色“有风险”，依据是**角色（域控是高价值目标）**，不是图谱预测出来的。

**为什么没用 Cognee 的语义搜索做入口：** 测试发现，拿原始命令行去搜技术描述效果很差（会命中 Netsh Helper DLL 之类无关技术），而本地没有 LLM 把命令行改写成自然语言。与其展示不准的东西，不如只从 Qdrant 确认过的技术出发。

### ⑤ 报告
- **默认是“有依据的模板”**：所有句子都由前面步骤的真实结果拼出来（受害机、IOC、技术、组织、预测、缓解），逐词流式输出。
- **如果本机开着 Ollama**（`localhost:11434`），执行摘要会自动改由本地模型写，默认模型 `qwen2.5:7b`，可用环境变量 `LOCAL_LLM_MODEL` 修改。
- 附带生成一条 **Sigma 规则**：Office/WmiPrvSE 启动的编码 PowerShell，且 base64 里包含下载执行特征，同时排除 Intune 的 `AgentExecutor.exe`。

## 五、3D 界面说明（frontend/src/stage.js）

| 效果 | 实现 |
|---|---|
| 网络拓扑 | 3d-force-graph，节点位置按网段排成“花瓣”（固定坐标，不乱飘） |
| 发光 | UnrealBloomPass 后期泛光 + 每个节点的加色光晕贴图 |
| 流量粒子 | 连线上的方向粒子，正常青色、攻击路径红色加速 |
| 告警冲击波 | 线框球 + 圆环从节点向外扩散 |
| 扫描波 | 从 WS-FIN-07 发出，**波到达哪台主机才揭示它的状态**（按距离延时） |
| 横向移动弧线 | 贝塞尔曲线管道，逐段“生长”出来 |
| 知识图谱 | 同一个 3D 画布切换数据，按节点类型着色：红=事件/观察到的技术，紫=组织，黄=预测，绿=缓解 |

界面布局：左边是告警队列和实时日志滚动，中间是 3D 舞台，右边是 Copilot 分步卡片，下方是 **Qdrant/Cognee 查询日志**（显示真实请求和毫秒耗时，给懂行的观众看）。

```

  attack.py        解析 ATT&CK STIX JSON 和 Sigma 规则 zip
  scenario.py      公司拓扑 + 日志生成（攻击链、干扰项都在这里）

  embed.py         FastEmbed 稠密/稀疏向量

  app.py           FastAPI 接口：/api/analyze /api/hunt /api/graph /api/report
frontend/
  src/main.js      演示步骤状态机（按空格推进）、右侧卡片、查询日志
  src/stage.js     3D 舞台与所有特效
  src/style.css    界面样式
run.sh             一键启动（缺什么自动下载）
```

**常见调整位置：**
- 改攻击故事 / 受害机 → `scenario.py`，改完执行 `uv run python -m backend.build --skip-graph --skip-kb`（只重建日志，几秒钟）
- 改失陷判定阈值 → `copilot.hunt()` 的 `z_threshold`
- 改归因/预测规则 → `copilot.reason()`
- 改演示节奏、动画时长 → `main.js` 里的 `sleep(...)`
- 改完前端要重新打包：`cd frontend && node build.mjs`

## 七、上台可能被问的问题

**Q：数据是真的吗？**
A：知识库是真的（MITRE ATT&CK 官方数据 + SigmaHQ 开源规则）；日志是合成的，但检索、排序、归因全部是真实计算，没有写死结果。

**Q：为什么不直接用 LLM？**
A：安全场景要求可追溯、不幻觉。检索和图谱给出的每个结论都能指回具体规则或 ATT&CK 关系；LLM 只（可选地）负责写摘要。

**Q：Recommend 和普通搜索差在哪？**
A：普通搜索只能说“像这个”，Recommend 可以同时说“像这个、但不像那些”。分析师把确认过的误报丢进反例，后续狩猎就自动避开这类噪音。

**Q：规模能扩展吗？**
A：Qdrant 的 `group_by`、payload 过滤、混合检索都是服务端能力，演示中每次查询只要几毫秒；真实环境可以按时间窗口和主机建索引，把事件量扩到千万级。

**Q：Cognee 在这里的价值是什么？**
A：向量检索回答“什么相似”，图谱回答“谁、接下来会做什么、怎么防”。而且事件会写回 Cognee 成为记忆，下一次调查可以直接关联。

**Q：归因准吗？**
A：只能说是“TTP 重合度最高的候选”，不是定论。真实归因需要基础设施、恶意软件样本等更多证据。（主动这样说，会显得很专业。）

## 八、运行与排障

```bash
./run.sh            # 启动（首次自动下载 Qdrant/数据并导入）
./run.sh --build    # 强制全部重建（约 13 分钟，主要花在 Cognee 写图）
```

| 现象 | 处理 |
|---|---|
| 页面空白 / 接口报错 | 看 `storage/app.log`；确认 `curl localhost:6333/healthz` 正常 |
| 端口被占用 | `pkill -f "uvicorn backend.app"` 后重启 |
| 想重来一遍演示 | 页面按 `R` 刷新即可（后端状态会被新一轮覆盖） |
| 投影分辨率不是 1080p | 浏览器缩放调到 100%，按 `F` 全屏；1400px 以下宽度会自动收窄右侧面板 |

**演示当天清单：** 提前运行并完整点一遍（预热模型）→ 断开 Wi-Fi 再排练一次 → 全屏 → 按 README 里的英文讲稿走。
